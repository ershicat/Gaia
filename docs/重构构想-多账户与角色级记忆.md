## 0 · 一句话概括这次改动

把「角色预设」从**人格模板**升级为**完整账户**：每个角色是一整套独立的系统
（人格 + 记忆库 + 原文档案 + 配角库 + 会话 + 全部设置 + 外观），
`Gaia` 只是承载这些账户的容器；角色卡与记忆包随之重新定义为**账户的可分发快照**。

## 1 · 为什么现在要做（问题起源）

### 1.1 记忆系统"难做"的真正原因（项目所有者的判断）

> 「目前的记忆系统难做是因为要满足两套机制，一套是对官方 ds 旧会话的索引，
> 另一套是角色级新会话的记录，两套机制是会冲突的。」

这个判断是对的，而且可以逐条落到代码上。下面第 2 章展开。

### 1.2 现在最严重的隐性缺陷：记忆是全局的

| 事实 | 证据 |
|---|---|
| 记忆文件库**没有任何角色过滤** | `features/memory/middleware.ts:44` `const files = memoryFiles()` —— 全量注入 |
| 整理时读写的也是同一份全局库 | `features/memory/consolidate.ts:203` `const next = [...files]` |
| 水位按会话记、库按全局共享 | `features/memory/files.ts:86-101`（`watermarks` / `lastRun` 按 sessionId，但 `files` 是全局一份） |

**后果**：两个角色时，A 角色的 `/people/人物A.md`、`/topics/领域A.md` 会被注入到 B 角色的会话；
B 会话"做梦"整理出的剧情事实也会写进 A 那份 `/topics` 文件。**交叉污染且不可逆**（写进去就分不出来）。

### 1.3 角色卡已经承载了部分"角色级"语义，但只做了一半

| 已是角色级 | 证据 |
|---|---|
| 聊天页背景图 + 不透明度 | `features/roles/contract.ts:19-22` `background` / `backgroundOpacity` |
| 角色内用户画像 | `contract.ts:17-18`，注释原文「**角色内用户画像：跨会话、不跨预设**」 |
| 系统提示词 / 温度 / 技能 / 开场白 / 头像 | `contract.ts:4-26` |
| 会话空间 | `roles/sediment.ts:11-18` 按 `roleIds` 过滤，角色之间互相看不到 |

**但设置与外观仍然是全局的**（见第 5 章 21 个键）。所以现在"切角色"只换了人设与会话，
没有换"这一整套系统"。

## 2 · 核心洞察：两套机制为什么必然冲突

### 2.1 两套机制的定义

| | 机制 A：官方 DS 旧会话的**索引** | 机制 B：角色级新会话的**记录** |
|---|---|---|
| 数据来源 | `deepseek_data-*.zip`（DS 官方导出） | 用户在角色账户里新建的会话 |
| 落位 | `roles/store.ts:97-100`：`roleIds:[内置角色]`、`noPersona:true` | `roleIds:[当前角色]` |
| 目标 | 能翻、能搜、能续聊、能取材（提炼角色卡/记忆） | 记忆生长、防 OOC、控成本 |
| 需要的特性 | **只读为主**：不改原文、不注入人格、不做时间线压缩；核心是**检索与定位** | **读写**：压缩 + 整理 + 召回 + 档案卡 |
| 失败模式 | 被别的东西污染/改写 → 索引失真 | 记不住/记错人 → OOC |

### 2.2 冲突的六个具体点（全部有代码证据）

**冲突 1 · 同一个文件库，两个写入方**
`consolidate.ts:203` 整理时取全局 `files`；A 与 B 两套会话整理进同一批 `/topics/*.md`。
→ 角色记忆里混入官方旧会话的闲聊事实。

**冲突 2 · 注入不分归属**
`middleware.ts:44` 全局注入。官方旧会话续聊时，角色A的长期记忆被塞进这段"历史"里；
反过来角色A的会话也会被灌入旧会话整理出的事实。

**冲突 3 · 档案卡的两种语义被混用**
`seeds` 表是"角色卡预置卡，给该角色的新会话用"（`cardStore.ts:77-88` + `store.ts:161-177`），
但旧会话本身也会被 `maybeBuildCard` 建档（只看轮数 ≥40，`store.ts:262`）。
→ 给一段"历史记录"套上一张人设卡，然后每轮注入。

**冲突 4 · `noPersona` 与记忆注入自相矛盾**
`noPersona` 的定义是"不注入角色提示词，保持原有上下文"（`roles/middleware.ts:6-9` 注释），
但记忆中间件**照旧注入全局长期记忆与档案卡**。→ 说保持原样，实际塞了别的东西。

**冲突 5 · 压缩与建档的策略互斥**
已有档案卡的长会话**跳过压缩**（`middleware.ts:37` `cardMode`、`store.ts:431`）。
→ 旧会话一旦建了卡就永不压缩，长度全靠 30 轮窗口；可旧会话真正需要的是**检索**，不是摘要。

**冲突 6 · 成本模型错位**
旧会话 6929 条，若按机制 B 的方式每轮带窗口 + 摘要 + 召回，成本高且收益低（用户多数时候只是在翻记录）；
而"索引"场景真正需要的是：**用户主动搜到那一段，才把它带进来**。

### 2.3 更深一层的判断：素材与记忆的**信任等级**不同

- **素材** = 未经选择的历史原文（可能混杂多个 RP、无关闲聊、多天多条线）
- **记忆** = 经过整理/确认的、当前角色有效的事实

把素材直接当记忆注入 = 把噪音当知识。这就是"忘记忆/串味"体感的来源之一。

### 2.4 结论

这不是实现细节问题，是**目标不同**：A 要"检索"，B 要"沉淀"。
用一套中间件同时干两件事，必然互相污染。

**账户模型的价值就在这里**：它从**结构上**把两者分开放——

```
机制 A → 内置账户（素材库）：只读、可检索、不进上下文、不整理
机制 B → 各角色账户：读写、压缩、整理、召回、档案卡
```

所以"以角色为记忆单位"不是概念美化，是**这个冲突的正解**。

## 3 · 目标结构

```
Gaia（容器 / 相当于一台设备）
│
├── 内置账户「Gaia」（不可删）= 素材库 / 收件箱
│   ├── 会话：从 DS 官方导出的全部聊天记录（noPersona，保持原样，可续聊）
│   ├── 原文存档：按会话导出的原文（可检索、可取材）
│   └── 记忆库：续聊时产生的记忆（机制 B，但归属内置账户）
│
├── 账户「角色A」= 独立的整套系统
│   ├── 人格模板（表层）：系统提示词 · 画像 · 温度 · 技能 · 开场白 · 头像 · 背景图
│   ├── 记忆库（里层）：/profile /people /topics /areas
│   ├── 原文档案（里层）：对话原文
│   ├── 配角库
│   ├── 会话们 + 会话状态（档案卡 / 摘要 / 水位）
│   └── 设置与外观：模型 · 上下文 · 压缩 · 记忆模型 · 音色 · 皮肤 · 气泡 …
│
└── 账户「角色B」= 独立的整套系统 …
```

**关键语义**：记忆不是"关联到角色"，是角色**内部的一层**。没有外键，没有跨角色共享。

## 4 · 数据放哪：一条清晰的分界线

| 类型 | 放哪 | 例子 |
|---|---|---|
| **用户可见 / 要备份 / 要发给别人** | **磁盘账户目录** | 记忆库、原文档案、角色卡、配角库 |
| **运行时 / 派生 / 缓存** | **IndexedDB（单库，记录带 accountId）** | 会话、档案卡、摘要、水位、向量/索引 |

不建议 IndexedDB 按账户分库（库名动态化会牵扯建库版本、迁移、删账户清理，坑多）；
**加 `accountId` 字段**足够，且现有会话表已经按 `roleIds` 过滤。

### 4.1 账户目录结构（建议）

```
accounts/
├── gaia-0a1b2c3d/                     ← 内置账户（素材库），目录名固定可读
│   ├── 账户.json                       ← accountId / 名称 / 创建时间
│   ├── 角色卡.json                     ← 表层人格模板（ST 兼容）
│   ├── 记忆库/
│   │   ├── profile.md
│   │   ├── preferences.md
│   │   ├── people/<人名>.md
│   │   ├── topics/<领域>.md
│   │   └── areas/<事>.md
│   ├── 原文/<会话标题或日期>-<会话id8>.md
│   └── 配角库.json
└── 角色A-a1b2c3d4/
    └── …（同上）
```

- **账户身份 = `<角色名>-<短id8>`**：名字可改、id 不变；`accountId` 写进角色卡 `extensions.gaia.accountId`
- 目录放在哪取决于文件系统方案（第 6 章）
- 会话状态（档案卡/摘要/水位）**不进目录、不进卡**，留在 IndexedDB 并带 `accountId`

### 5.2 三分法

| 类别 | 项 | 理由 |
|---|---|---|
| ✅ **应该账户级** | 模型、思考、搜索、上下文轮次、自动压缩、压缩阈值、记忆整理模型、会话档案开关、音色、标题提示词/自动标题、皮肤、气泡、主题背景、字体缩放、折叠思考、侧栏状态 | 直接影响"这个角色的体验与成本" |
| ⛔ **必须全局** | `chat-demo:api-key` | 角色级 → N 个角色填 N 次 key，换 key 改 N 处，是灾难 |
| ⛔ 必须全局 | `gaia:user-name` / `gaia:user-avatar` | "我"是账号主人；角色级画像已在 `Role.profile`，两层不冲突 |
| ⛔ 必须全局 | `chat-demo:locale` | 产品界面语言，不该切角色就换 |
| ⛔ 必须全局 | `gaia:update.seen` | 公告已读一次就够 |
| ⛔ 必须全局 | 余额 / 诊断日志 / 原生下发的 `__GAIA_CONFIG__` | 同一账号、同一设备 |
| ❓ **灰区待定** | `gaia:theme-layout`（界面骨架 classic / 微信壳） | 切角色换整屏骨架会很晕；倾向全局 |
| ❓ 灰区 | `chat-demo:theme-preference`（light/dark） | 跟随系统 vs 每角色一套 |
| ❓ 灰区 | `chat-demo:location` | 是"你"的属性（影响时间/天气上下文），倾向全局 |
| ❓ 灰区 | `gaia:providers` + `gaia:api-base` | 每角色一套服务商技术上可行，但排查困难 |

### 5.3 实现机制（三个前提）

**a. 键注册表（先做这个）**
把全部键集中到一个 registry，读写只走单一入口（`scope.read(key)` / `scope.write(key, value)`）；
禁止任何文件再直接 `localStorage.getItem('gaia:…')`。
**这是"每角色一套"能可靠工作的前提**——现在键散在 6 个文件里，漏一个就是新的串味 bug。

**b. 账户作用域 + 单一切换入口**
```
存储键 → gaia.acct.<accountId>.<原键名>
switchAccount(id)：读该账户全部键 → 一次性覆盖内存态 → 触发重渲染
```
挂点现成：`app/compose.ts:57` 已订阅 `roles:activeChanged`（现在只做 `newChat()`），加一步 `switchAccount()`。

**c. 边界规则怎么绕**
`services/` 不许 import `features/`（`scripts/check-deps.mjs`），而账户 id 在 roles 块里。
办法：复用现有注入模式，像 `platform/chat.ts:21` 的 `setChatBridge` 那样由装配层注入 `setAccountScope(id)`；
或直接用 `platform/runtime.ts:12-16` 已有的 `setActiveRoleId()` 挂点。

## 6 · 文件系统：Android 的真实约束

### 6.1 现状（实测）

`android/AndroidManifest.xml` 只有 3 个权限：`INTERNET` / `RECORD_AUDIO` / `MODIFY_AUDIO_SETTINGS`，**零存储权限**。
写文件只能落 `Downloads/Gaia`（`MainActivity.java:376-389` 走 MediaStore，Android 10+ 免权限）；
读只能靠系统选择器给的一次性 URI。

### 6.2 四种做法

| 方案 | 权限 | 用户能在文件管理器看到 | 能读用户自己放进去的文件 | 工作量 |
|---|---|---|---|---|
| **A** 私有目录 `Android/data/com.gaia.app/files/accounts/` | 0 | ❌ Android 11+ 进不去 | — | 最小 |
| **B** `Downloads/Gaia/accounts/`（MediaStore） | 0 | ✅ 下载/Gaia 里可见 | ⚠️ 分区存储基本只能看自己写的 | 小 |
| **C** SAF 目录树（用户点一次选文件夹） | 0，用户授权一棵树 | ✅ 任意目录，如 `Documents/Gaia` | ✅ 完整 | 中（原生加 picker + 文件 API） |
| **D** 「所有文件访问」特殊权限 | 需用户去系统设置手动开 | ✅ 全盘 | ✅ 完整 | 中（各 ROM 提示文案吓人） |

### 6.3 建议：C 为主 + A 兜底

- C 是唯一同时满足「用户能看见 / 拷走 / 塞进来」+「零敏感权限」的方案
- A 保证用户拒绝授权时应用照常可用（记忆在私有目录）

### 6.4 实现捷径：复用现有本地服务器

`android/src/com/gaia/app/LocalServer.java:188` 已有 `/__gaia/config.js` 这类特例路由。
再加 `/__gaia/fs/{list,read,write}` 三个端点，web 侧直接
`fetch('http://127.0.0.1:47831/__gaia/fs/…')` 读写——**同源、无 CORS、不用新增 JS bridge 通道**。

### 6.5 磁盘 / IndexedDB 混合策略

| | 纯 IndexedDB（现状） | 纯磁盘 |
|---|---|---|
| 用户可见 | ❌ 看不见，备份只能靠导出 | ✅ 直接翻文件夹 |
| 性能 | ✅ 内存态 | ❌ 每轮读文件 |
| 用户手改 | ❌ 改不了 | ✅ 但要重扫 |

建议：**磁盘是真源，IndexedDB 是索引 + 缓存**
```
写：磁盘 → 索引 → 内存态（磁盘失败则内存态 + 待同步标记）
读：召回走内存索引；注入读缓存正文；mtime/size 变了才重读
启动：扫账户目录建索引（24–60 个文件，毫秒级）
外部改动：靠 mtime 差异懒重载（用户自己编辑记忆 → 下次请求生效）
```

## 7 · 角色卡与记忆包的重新定义

### 7.1 卡不再是"记忆容器"，是**账户的可分发快照**

```
导出包（zip，fflate 已在用：services/chat/history/zipReader.ts + zipWriter.ts）
├── 角色卡.json       ← 表层，ST 兼容：name/description/first_mes/extensions.gaia.{accountId,profile,temperature,skills}
├── 记忆库/            ← 里层（可选带）：profile/people/topics/areas
├── 原文/              ← 里层（可选带）：对话原文
├── 配角库.json        ← 账户资产（可选带）
└── account.json      ← accountId / 导出时间 / 版本
```

- **导出** = 把账户目录打包
- **导入** = 解到新账户目录；`accountId` 决定是"新账户"还是"接回旧账户"
- 包里同时有 ST 兼容的 `角色卡.json` 与人类可读的 `记忆库/`，别的客户端也能只读人设

### 7.2 体积实测（重要）

| 项 | 数字 |
|---|---|
| 样本会话（最高执政官） | 6929 条消息，21 天（2026-10-29 → 11-19） |
| 对话正文 | **1,413,524 字**（我 70,492 / 角色 1,343,032） |
| 思考内容 | 570,640 字 |
| 正文 UTF-8 | ≈ 4.24 MB |
| 现有角色卡换算法 | `角色A.chara_card_v2.json` = 44,590 字记忆 → **146,174 B**（×3.28 B/字，含 JSON 转义） |
| ⇒ 全量原文塞进单张 `.json` 卡 | ≈ **4.6 MB**（不含思考）；含思考 ≈ 6.5 MB |
| ⇒ 打包压缩后 | ≈ 1.5–2 MB |

**结论**：不要再往 `chara_card_v2` 的 JSON 字符串里塞原文。用目录 + zip。

### 7.3 ⚠️ 隐私约束

原文随卡走 = 把与 AI 的全部原始对话（1.4 MB）一起发出去。
建议分两种导出：

| 导出模式 | 内容 | 体积 | 用途 |
|---|---|---|---|
| **只带提炼记忆**（默认） | 角色卡 + 记忆库 | ≈ 150 KB | 发给别人 |
| **带原文档案**（显式勾选） | 再加 原文/ | ≈ 1.5–2 MB | 只给自己换机备份 |

## 8 · 新用户路径：从 DS 官方导入聊天记录

这是目前最重要的拉新点，**与新模型不冲突，因为现有落位本来就是对的**。

### 8.1 现状事实

| 环节 | 代码 | 行为 |
|---|---|---|
| 导入归属 | `features/roles/store.ts:97-100` | `source==='import'` → `roleIds:[内置角色]`、`noPersona:true` |
| 列表过滤 | `features/roles/sediment.ts:11-18` | 角色之间互相看不到；无 `roleIds` 的会话算内置角色的 |

⇒ DS 导出的聊天记录**全部住在内置账户**，在账户模型下它就是**素材库 / 收件箱**。

### 8.2 新用户完整流程（零选择）

1. 装 APK
2. 导 `deepseek_data-*.zip`（`features/settings/ui/DataPage.tsx:144` 已支持 `.zip`，`importArchive` + `zipReader` 现成）
3. 会话全进内置账户：可浏览、可搜索、**可继续聊**（`noPersona` 保持原样）
4. 挑一段会话 → **「取材做角色」** → 生成角色卡 + 记忆库 → 新建账户
5. 之后该角色的记忆在自己的账户目录里独立生长

**第 4 步就是已经跑通的那套方法**（`gaia-packs/方法-有历史会话做角色卡.md`）：
以前是手工跑脚本（`gaia-packs/*/tools/build-card.py` / `build-memory.py`），素材库是它缺的应用内入口。

### 8.3 一个现存 UX 坑（必须修）

导入后必须**切到内置角色「Gaia」**才看得见这些会话（`sediment.ts:11-18`）。
停在其他角色时用户会觉得"导入没成功"。账户模型下会更明显。
→ 导入成功后自动切到内置账户 + 提示一句。

## 9 · 迁移（线上已有用户，最高风险项）

### 9.1 现有全局记忆的搬运

`gaia.memory.files` 里的文件没有 accountId（结构只有 6 个字段），迁移时无法自动判断归属。
建议规则：

1. 检测到旧全局记忆 → 建/选一个账户（默认当前活跃角色对应的账户；若当前是内置角色则进素材库）
2. 全部文件搬进去（保留 path 结构）
3. 面板里给每个文件一个"改归属账户"的下拉（最低成本的可修正手段）
4. 旧库**保留不删**，写迁移标记（可回滚）
5. 老包重放仍按"同名 path 跳过"语义 → 迁移完再导旧包是无害的

### 9.2 21 个全局键的搬运

首次启动把现有全局键**复制**到默认账户（内置角色），**原键保留不删**（回滚保底）。
否则升级后用户的模型 / 背景 / 开关全部回默认值——这是最容易招致投诉的点。

### 9.3 平滑性要求

- 迁移失败**不阻断启动**、不清空、不半写覆盖；`diagError` + 下次启动重试
- 迁移完成后给一条可查的自检输出（面板或诊断）：
  `迁移前 files=N / cards=M / seeds=K / summaries=S` → 迁移后同量级
- 用户手机上没控制台，**只有这条输出能证明"我的记忆还在"**

### 15.2 与「角色小手机」的对齐（新增认识）

项目所有者 2026-11-22 定调：将来做的**角色小手机**必须**与 Gaia 联动**——Gaia 里建的角色会自动建立一个「小手机」实例账户，角色在聊天中能改动这台手机（换壁纸、发动态、发消息）。

**本构想的「账户」就是小手机要的「实例账户」，不要建第二套概念。** 对齐关系：

| 本构想的 | 小手机直接复用 |
|---|---|
| 账户 = 角色的一整套系统（§3） | 就是小手机的实例账户；「建角色 → 自动建实例」= 建账户 |
| 账户身份 `<角色名>-<短id8>` + 卡内 `accountId`（§4） | 实例 id 直接用它（改名不丢、换机可接回） |
| 账户目录 `accounts/<名>-<id8>/`（§4.1） | 手机的壁纸 / 动态 / 相册 / 未读等状态放这里，随导出包走 |
| 账户级设置（§5.2） | 「这台手机长什么样」天然账户级；切角色即换皮 |
| `switchAccount(id)` 单一切换入口（§5.3b） | 小手机切换走**同一个**入口，不新建第二个 |
| 记忆在账户内部、无外键（§2.4、§3） | 小手机**不碰记忆**，只碰自己的状态，避免又一条污染 |

**因此建议在 §10 分期后面新增：**

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **6** | **角色小手机**（皮肤层 → 联动层） | **硬依赖阶段 1**；要带状态则依赖 3/4 |

小手机设计细节另见 `功能库.md` §11.2④（两层结构、小组件清单、only max 实机参考、模型如何"控制"手机的三条路径与五条硬约束）。
