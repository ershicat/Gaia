# 世界书（Lorebook）实现方案 —— 暂不实现，与「群组」一起做

> 状态：**只留方案，本轮不做**。用户要求：世界书属于高阶能力，要和「群组」（多角色同会话）一起做，
> 否则做出来只是"单角色的关键词注入"，价值不完整。
>
> 参考实现：RikkaHub（AGPL-3.0，`app/src/main/java/me/rerere/rikkahub/data/model/Assistant.kt`
> 与 `data/ai/transformers/PromptInjectionTransformer.kt`）。**只学行为，不拷代码。**

---

## 1. 它解决的问题

角色卡是"常驻设定"，世界书是"**按需召回的设定**"：

- 常驻设定（system prompt）里的东西，每轮都占 token；写多了模型反而抓不住重点。
- 世界书把设定拆成一条条「关键词 → 内容」，只有当最近几条消息里出现关键词时才注入。
- 典型场景：角色卡写"北欧小镇的旅店老板娘"，世界书里存「酒馆」→「镇上唯一酒馆叫断角鹿，
  老板是退役佣兵，二楼有赌局」。用户提到酒馆才注入，不提就不花钱。

## 2. 数据结构（参考 RikkaHub）

```
Lorebook {
  id, name, description, enabled,
  entries: [Entry]
}

Entry {
  id
  keywords: string[]        // 触发词
  useRegex: boolean         // 是否按正则匹配
  caseSensitive: boolean    // 大小写敏感，默认 false
  scanDepth: number = 4     // 只在最近 N 条消息里找触发词
  constantActive: boolean   // 常驻激活：无条件注入
  injectDepth: number = 4   // AT_DEPTH 位置时，插在倒数第 N 条之前
  position: BEFORE_SYSTEM_PROMPT | AFTER_SYSTEM_PROMPT | TOP_OF_CHAT | BOTTOM_OF_CHAT | AT_DEPTH
  role: USER | ASSISTANT    // 注入成谁说的话
  priority: number = 0      // 越大越先，同位置按此排序
  content: string           // 注入正文
  enabled: boolean
}
```

RikkaHub 里世界书是**全局池**，通过 `assistant.lorebookIds` 绑定到助手；
与我们现在的"角色 = 助手"对应，即 `Role.lorebookIds`。

另外它还有一类**模式注入（ModeInjection）**：没有关键词，跟着开关生效的注入，
结构相同、触发恒真。做群组时会用到（例如"群聊主持规则"）。

## 3. 触发与注入算法

```
1. 取最近 scanDepth 条非 SYSTEM 消息，join('\n') 成匹配文本
   （每条消息取纯文本，忽略图片/文件）
2. 对每个 entry：enabled && (constantActive || keywords 命中)  → 触发
   - 普通匹配：文本包含关键词（默认忽略大小写）
   - 正则匹配：new RegExp(keyword, caseSensitive ? '' : 'i').test(text)
   - 正则写错不要抛异常打断请求，当作不命中
3. 所有触发的注入按 priority 降序，按 position 分组
4. 按位置落地：
   - BEFORE_SYSTEM_PROMPT：拼在原 system 前面
   - AFTER_SYSTEM_PROMPT：拼在原 system 后面
   - TOP_OF_CHAT：插在第一条 user 消息之前
   - BOTTOM_OF_CHAT：插在最后一条消息之前
   - AT_DEPTH：插在倒数第 injectDepth 条之前（多条同深度合并）
5. 同位置、同 role 的多条注入合并成一条消息，标记 synthetic（导出/统计时要能识别并跳过）
6. 插入前做安全对齐（见第 4 节）
```

## 4. 安全插入（必须抄的一条细节）

不能把注入消息插在「USER → 带工具调用的 ASSISTANT」之间，DeepSeek 会报错或打断推理连续性。
做法：目标位置往前回退，直到不再是 `prev=USER && cur=ASSISTANT(含 tool_use/tool_result)`。

## 5. 在我们这套 web 架构里怎么落

- 位置：`features/` 新积木 `lorebook`（纯 web，不碰 native）。
- 数据：IndexedDB（与角色卡同库），`Lorebook` 与 `Entry` 两种记录，角色上存 `lorebookIds`。
- 接入点：**请求中间件**（`platform/pipeline.ts`）。
  - 现有 `roles` 积木的 `middleware.ts` 负责拼人格 → system；
  - 世界书中间件排在它之后：读到 `roleIds` 对应的世界书，按上面算法改写 `ctx.system` 或插入消息；
  - 需要给 `RequestContext` 增加"额外注入消息"字段（现有结构只有 system/temperature 等），
    或者在 roles 的 persona 组装阶段直接拼进 system（TOP_OF_CHAT / AT_DEPTH 这类位置做不到，只能放 system）。
  - 结论：**做世界书要扩 `RequestContext`**（加 `injections: {role, position, depth, content}[]`），
    由 store 在组装 messages 时落地，而不是只拼 system。
- UI：角色编辑页里新增「世界书」入口：列表 → 条目编辑（名称/关键词/正则/深度/位置/优先级/内容/常驻开关），
  支持导入 SillyTavern 世界书 JSON（`entries` 的 `key`/`keysecondary`/`content`/`constant`/`selective`）。
- 群组：群组会话里可以有多个角色，世界书来源 = 所有参与角色的绑定的并集，去重后统一触发；
  这正是"和群组一起做"的原因——单角色时它只是个关键词开关，群组时才真正承担"世界观管理"。

## 6. 验收口径（做的时候照这个验）

1. 关闭世界书：请求体与原样一致（可对比 network 抓包）。
2. 关键词命中：system/消息里出现注入内容；不命中：不出现。
3. scanDepth=1 时只看最后一条；depth 越界不崩。
4. 正则写错：不抛异常、不命中、其余注入照常。
5. 注入插在 user→assistant(tool) 之间的情况被回退到安全位置。
6. 常驻激活条目始终注入，且不参与关键词匹配。
7. 导出会话/导入会话：synthetic 注入消息不被写进历史（避免污染用户数据）。
