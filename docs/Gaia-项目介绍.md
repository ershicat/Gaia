## 0 · 一页速览

| 项 | 值 |
|---|---|
| 名字 | Gaia（盖亚） |
| 形态 | 安卓 WebView 壳 + 自己重写的前端，**全程只有一个 Activity** |
| 定位 | 面向 **AI 角色扮演/长期陪伴**的聊天客户端（不是通用助手） |
| 前端来源 | DeepSeek 官方 `chat-demo` 0.1.1 的**干净 fork**（不是注入、不是补丁、不是套壳浏览器） |
| 技术栈 | React 18 + rspack 2 + zustand 4.4.7 + TypeScript strict（`tsc --noEmit` 零错误） |
| 代码量 | 前端 **229 个文件 / 26,032 行 / 881 KB**（不含依赖与构建产物） |
| 安装包 | ≈ **2.08 MB**（web 资源 + dex 打进 assets，不用 Gradle） |
| 后端 | **零后端**。直连 13 家服务商 API，数据全在本机 IndexedDB |
| 版本节奏 | 2026-11-18 起，4 天做到 1.8.15；一天最多一个正式版，中间用 `beta.N` |
| 落点 | 自用/小范围内测；无云同步、无账号 |

**一句话总结现状**：功能已经比较完整（记忆、角色卡、主题、多服务商、两套界面骨架），但**记忆是全局的**，这是目前最大的结构性缺陷（见 §4.6），也正是我想做的重构的起点（§7.5）。

## 1 · 它是什么（以及不是什么）

### 1.1 是什么

一个**给角色扮演用的聊天客户端**。核心诉求不是"问答"，而是：

- 一个角色能陪我聊**几个月、几千轮**，还记得住剧情、称呼、发生过的事；
- 角色之间要有**独立记忆**，不能串味；
- 角色本身要能**打包搬走**（换手机、发给别人）；
- 这些都要在**手机上**顺滑，且**成本可控**。

### 1.2 不是什么

| 不是 | 说明 |
|---|---|
| 不是浏览器套壳 | 前端是官方 demo 的干净 fork，源码级改造；无 DOM 注入、无 CSS hack |
| 不是酒馆（SillyTavern）的移动端皮 | 借鉴了它的角色卡格式（`chara_card_v2`）与 lorebook 思路，但记忆系统是自己重写的 |
| 不是云端产品 | 没有服务器、没有账号体系。API Key 存在本机，请求直连服务商 |
| 不是通用 AI 助手 | 有余额/诊断这些运维功能，但没有联网搜索之外的工具生态 |

### 1.3 为什么自己做（动机）

| 现成方案的痛点 | 我的判断 |
|---|---|
| 官方 App | 不能自定义记忆与角色卡；上下文策略是黑盒 |
| 酒馆（SillyTavern） | 功能强、生态好，但桌面 Web 形态，手机上体验差；注入式改造重 |
| 通用助手 App | 不关心"角色长期一致性"，也几乎都不给看缓存/成本 |

所以选了"官方 demo fork + 自建原生壳"这条**自己能完全掌控上下文装配**的路。

## 2 · 技术底座

### 2.1 三层积木架构（依赖单向）

```
L0  platform/     插槽 / 事件 / 请求管线 / 会话过滤器 / 只读句柄 / 开关 / 运行期参数
L1  features/*/   每块功能一个目录，互相禁止 import
L2  app/compose   唯一允许同时看见多块（和上游 store）的地方
```

- **边界由工具强制**：`scripts/check-deps.mjs` 在构建期扫描，`features/A` 引用 `features/B` 直接让构建失败；`platform` 不许引用 `features/`。
- **故障隔离**：每个插槽独立 `ErrorBoundary` + 每块有开关；一块崩了只那一块空白，整场会话不崩。
- **为什么这么设计**：功能会一直加，而我不想每加一个功能都去改一圈别人的代码。跨块只走三种渠道——类型化事件、插槽、装配注入。

当前 13 块积木：
`host` `profile` `roles` `cast`(配角) `memory` `usage` `account` `providers` `settings` `theme` `intro` `diagnostics` `shell`

### 2.2 原生壳（极少，只做浏览器做不到的事）

| 能力 | 实现 |
|---|---|
| 承载体 | 单个 `MainActivity` + 一个 `WebView` |
| 本地静态服务 | 内置 `LocalServer` 监听 `127.0.0.1:47831`，把打包进 assets 的前端当网页伺服 |
| 为什么固定端口 | IndexedDB 按 **origin** 隔离，端口一变历史会话就"看不见了" |
| 原生能力 | 录音（`RECORD_AUDIO`）、文件落盘（MediaStore → `Downloads/Gaia`，免存储权限）、返回键分级栈、启动参数注入 |
| 权限 | 只有 3 个：`INTERNET` / `RECORD_AUDIO` / `MODIFY_AUDIO_SETTINGS` |

**关键取舍**：不引入 Gradle，用 `aapt2` + `javac` + `d8` + `apksigner` 手工出包（`android/build.ps1`）。好处是构建快、依赖少；代价是要自己处理资源与签名细节。

### 2.3 数据都在本机

| 存储 | 放什么 |
|---|---|
| IndexedDB | 会话、消息、摘要、记忆文件、档案卡、配角库… |
| localStorage | 设置（21 个键：模型、上下文轮次、主题、字体…） |
| 磁盘（Downloads/Gaia） | 用户主动导出/导入的包（zip） |

没有后端 = 隐私好、无运营成本；代价是**没有跨设备同步**，换机只能靠导出包（见 §5.4）。

## 3 · 现在有什么功能

### 3.1 聊天与上下文

| 功能 | 说明 |
|---|---|
| 流式回复 + 思考过程 | 思考内容可自动折叠 |
| 上下文轮次上限 | 默认 30 轮；到上限按**滞回策略整体丢弃**，不逐轮滑（避免每轮都击穿缓存） |
| 自动压缩 | 到 80% 提前压；压缩后丢弃被覆盖轮次（`dropTurns`） |
| 重新生成 / 停止 | 停止会连队列与判断器一起取消 |
| 时间读数 | 每次提问附 ISO 时间戳（含偏移 + IANA 时区）、距上一条多久——**走尾注，不进 system** |
| 关键词召回 | 命中旧轮次时把片段放进请求**末尾** |
| 附件 | 图片等，落盘加固过（见 §8） |
| 朗读（TTS） | 单默认音色 |

### 3.2 角色

| 功能 | 说明 |
|---|---|
| 角色卡 | 系统提示词 / 温度 / 技能 / 开场白 / 头像 / 聊天背景（含不透明度）/ 角色内用户画像 |
| 导入导出 | **兼容 SillyTavern `chara_card_v2` / V1**；Gaia 自己导出的也能导回 |
| 卡内夹带 | 可带「预置会话档案卡」与「记忆文件」，导入时一并落地（同名记忆跳过） |
| 多角色隔离（部分） | 会话按 `roleIds` 过滤，角色之间互相看不到别人的会话 |
| 配角库 | **每会话一套配角档案**（名字/触发词/身份/说话方式/称呼/关系），命中触发词或标「常驻」才进上下文 |
| 会话档案卡 | 长会话自动建一张「人物/关系/世界观/剧情进度/未完成线索」的卡，**防 OOC** |

### 3.3 记忆

三套机制 + 两条召回，详见 §4。

### 3.4 主题与界面

| 功能 | 说明 |
|---|---|
| 主题商城 | 5 套配色 / 5 种气泡（含透明毛玻璃）/ 5 种背景 |
| 界面骨架 | **经典**（侧栏 + 主区）/ **微信**（底部四页：会话·通讯录·朋友圈·我） |
| 字体与外观 | 字号三档、浅色/深色/跟随系统、思考折叠 |

### 3.5 接入（多服务商）

13 家预设 + 自定义网关：国内 DeepSeek / Kimi / 智谱 GLM / 通义千问 / 火山方舟，海外 OpenAI / Gemini / Groq / Mistral / Anthropic，聚合 硅基流动 / OpenRouter，再留一个自定义网关。选好只填 Key。

- 两套协议层：OpenAI Chat Completions 兼容 + Anthropic 原生
- 按服务商降级：余额/语音/附件上传/上下文上限只有部分支持，不支持会直接告诉用户

### 3.6 运维与安全网

| 功能 | 说明 |
|---|---|
| 诊断日志 | 设备摘要 + 事件时间线，可导出 |
| 启动失败兜底页 | 装配/渲染/整包解析失败都能看到原因 + 重试/复制诊断/保存诊断/回经典界面/清数据 |
| 更新公告 | 每版一次，按版本号记「已读」 |
| 数据管理 | 会话导出导入、上传历史文件（支持 DeepSeek 官方 zip） |

## 4 · 基石一 · 记忆系统

> 这是整个项目最难、也最值得被指点的部分。

### 4.1 问题本身为什么难

角色扮演要"记住剧情"，但有三重硬约束：

1. **上下文有限**：几千轮对话不可能全带上。
2. **按 token 计费**：带得越多越贵，且长会话每句都在付费。
3. **一致性要求高**：记错人、记错时间线，用户立刻感受到（OOC）。

### 4.2 三套机制（互不替代，同时存在）

| 机制 | 模拟什么 | 存哪 | 注入方式 |
|---|---|---|---|
| **摘要压缩** | 短期记忆 | IndexedDB `gaia.memory` | 进 system（压缩时重写） |
| **长期记忆文件库** | 长期知识 | `gaia.memory.files` | `/profile` `/preferences` 全文进 system；其余只给标题+描述 |
| **会话档案卡（防 OOC）** | 当前剧情的"人设与进度" | `gaia.memory.card` | 作为**独立一条 user 消息**（`cardNote`），不进 system |

长期记忆是一个 Markdown 文件 = 一条记忆：`/profile.md`（用户是谁）、`/preferences.md`（怎么回答）、`/topics/*`（领域）、`/areas/*`（事）、`/people/*`（人）。空闲约 2 分钟后自动「做梦」整理（用模型把新对话蒸馏进这些文件），也可手动触发。

### 4.3 两条召回线（都不落库、实时算、只进尾注）

| 召回 | 做法 | 门槛 |
|---|---|---|
| **记忆文件召回** | 对 `/people` `/topics` `/areas` 正文做行级检索 | 词权按**文档频率**：df≤1 记 2 分、≤3 记 1.5、≤8 记 1、其余 0.5；4 字以上 ×1.5。「哥哥/姐姐/宝宝/亲爱/老公/老婆/主人/大人」等泛称与全虚词片段**权重归 0**。标题/描述/别名命中 +2。单行 ≥1.5 才算命中 |
| **原文档案召回** | `/archive/*` 里命中那句前后各取 2 条成段返回（单段截 1200 字） | 预算 750 token、最多 1 段、总分门槛 3，且**必须有一个「稀有词」锚点**（权重 ≥1.5）——防止泛问句把整段原文拉进来 |

**为什么加"罕见度加权"**：早期版本的召回老把"哥哥""姐姐"这种满篇都是的称呼当成"问的就是这条"的证据，导致召回出一堆无关片段、既贵又乱。改成按文档频率算权重后，只有专名（人名/地名/专有概念）才真正起锚点作用。

### 4.4 一次请求里到底装了什么（顺序即成本）

```
system（字节稳定段，只有这里能命中缓存）
  ├─ 上游基础系统提示词
  ├─ 角色提示词 / 技能正文
  ├─ 早前对话摘要（压缩后才有；有档案卡时不再注入）
  └─ 长期记忆（画像 + 回答偏好全文；其它文件只给标题和描述）

messages
  ├─ 固定窗口内的历史（默认最近 30 轮，整体丢弃不逐轮滑）
  ├─ [会话档案卡]（独立 user 消息，动态内容所以不进 system）
  ├─ [latest_reminder]（当前时间/时区，固定 5 字段格式）
  └─ 当前 user 消息（正文 + <附注> 尾注：时间读数、召回片段）
```

### 4.5 三条铁律（违反就变贵或报错）

1. **每轮都会变的字节绝不能进 system**，否则提示词缓存从第一个字节就作废。
2. `latest_reminder` 只接受 `<date>,<weekday>,<location>,<platform>,<language>` 五个字段，且后面必须紧跟一条 user 消息（不能塞中文自由文本，也不能连着放两条）。
3. 压缩会改写历史 → 必须同时关掉续写前缀（`prefixEnabled=false`），否则续写内容重复。

### 4.6 ⚠ 最大的结构性缺陷：记忆是全局的

这是我最想请教的现实问题（也是 §7.5 重构的起点）：

| 事实 | 后果 |
|---|---|
| 记忆文件库**没有任何角色过滤**（中间件直接读全量 `memoryFiles()`） | 两个角色时，A 的 `/people/人物A.md`、`/topics/领域A.md` 会被注入到 B 的会话 |
| 整理时读写的也是同一份全局库 | B 会话"做梦"整理出的剧情事实会写进 A 那份 `/topics` 文件 |
| 水位按会话记、库按全局共享 | 交叉污染**且不可逆**（写进去就分不出来是哪个角色的事） |

**根因不是实现细节，而是目标冲突**：这个 App 同时要服务两种场景——

| | 机制 A：官方历史会话的**索引** | 机制 B：角色级新会话的**沉淀** |
|---|---|---|
| 数据来源 | DeepSeek 官方导出的几千条旧聊天 | 用户在角色下新聊的会话 |
| 需要什么 | **只读为主**：检索、定位、续聊、取材 | **读写**：压缩、整理、召回、档案卡 |
| 失败模式 | 被污染 → 索引失真 | 记不住/记错人 → OOC |

两套机制共用一套中间件，**必然互相污染**。我目前的做法是靠"用户自己注意别混"，这是不体面的解法。

## 5 · 基石二 · 角色卡

### 5.1 格式：与酒馆生态兼容

导出/导入用 `chara_card_v2`（SillyTavern 标准），字段映射：

| 字段 | 对应 |
|---|---|
| `name` / `description` / `personality` / `scenario` / `first_mes` / `mes_example` | 角色基本人设 |
| `extensions.gaia.profile` | 角色内用户画像（跨会话、不跨预设） |
| `extensions.gaia.temperature` | 该角色温度 |
| `extensions.gaia.skills` | 技能（可插拔的提示词片段） |
| `extensions.gaia.sessionCard` | 预置会话档案卡（**仅导入方向生效**） |
| `extensions.gaia.memoryFiles` | 预置记忆文件（**仅导入方向生效**） |

**已知不对称**：导出只写 `profile` / `temperature` / `skills`，**不写** `sessionCard` / `memoryFiles`。所以现在的"夹带档案"是单向的：只能带进来，带不出去。这是我有意先做的保守版本（避免误把 1.4 MB 原文发给别人），但确实不完整。

### 5.2 导入行为

- 支持多文件批量导入，**逐文件报错**（一个坏不拖累其它）
- 同名**不合并**，每次新建一个角色
- 卡内夹带的档案卡进入"种子表"（`seeds`），该角色的**新会话首次发送前**自动落成正式档案卡，并顺手打开「会话档案」开关
- 记忆文件按 path 去重，同名跳过不覆盖

### 5.3 体积实测（决定"卡能不能当记忆容器"）

| 项 | 数字 |
|---|---|
| 样本会话 | 6,929 条消息、21 天 |
| 对话正文 | **1,413,524 字**（我 70,492 / 角色 1,343,032） |
| 思考内容 | 570,640 字 |
| 正文 UTF-8 | ≈ **4.24 MB** |
| 记忆换算法 | 44,590 字记忆 → 146,174 B 的 JSON（×3.28 B/字，含转义） |
| ⇒ 全量原文塞进单张 `.json` 卡 | ≈ **4.6 MB**（不含思考），含思考 ≈ 6.5 MB |
| ⇒ 打包压缩后 | ≈ 1.5–2 MB |

**结论**：不要往 `chara_card_v2` 的 JSON 字符串里塞原文。原文应该走"目录 + zip"。

### 5.4 我想要的最终形态（未实现）

把「角色预设」从**人格模板**升级为**完整账户**：一个角色 = 一整套独立系统（人格 + 记忆库 + 原文档案 + 配角库 + 会话 + 全部设置 + 外观）。角色卡随之重新定义为**账户的可分发快照**（zip：`角色卡.json` + `记忆库/` + `原文/` + `配角库.json` + `account.json`），并区分两种导出：

| 导出模式 | 内容 | 体积 | 用途 |
|---|---|---|---|
| 只带提炼记忆（默认） | 角色卡 + 记忆库 | ≈ 150 KB | 发给别人 |
| 带原文档案（显式勾选） | 再加 `原文/` | ≈ 1.5–2 MB | 只给自己换机备份 |

（这就是 §7.5 的重构构想。）

## 6 · 基石三 · 请求装配与成本纪律

> 这条经验可能是整个项目里最"值钱"的，也是最容易被忽略的。

### 6.1 核心事实：缓存是前缀逐字节匹配

DeepSeek 的提示词缓存：**只要前缀里有一个字节变了，从那一段往后全部按未命中计费**。所以真正决定成本的，不是"上下文多长"，而是"**前缀是否稳定**"。

### 6.2 实测数字

| 场景 | 输入 / 命中 / 输出 | 费用 |
|---|---|---|
| 会话第 1 轮 | in 8,248 · 命中 0 · out 222 | 0.91 分 |
| 同一会话第 2 轮 | in 1,246 · **命中 7,168（85%）** · out 233 | **0.23 分** |
| 另一会话第 1 轮 | in 6,375 · out 574 | 0.70 分 |
| 同一会话第 2 轮 | in 1,316 · **命中 5,120（80%）** · out 574 | 0.37 分 |

观察规律：

| 缓存命中率 | 含义 |
|---|---|
| 0% | 新会话，或 system 变了 |
| ~20% | **有东西改写了 system**（历史上是压缩时重写摘要造成的） |
| 73~85% | 正常。只有最后一轮的用户消息不同，尾注不落库所以永远差这一条 |

### 6.3 由此得出的设计原则

**长会话"两句话八毛"的根因，几乎总是"每轮都在改 system"，而不是窗口太长。**

所以本项目所有动态内容都遵守一条纪律：**静态的进 system，每轮变的只能进尾注**。

| 内容 | 归属 | 理由 |
|---|---|---|
| 基础系统提示词、角色提示词、技能、画像/偏好全文 | system | 字节稳定，可命中缓存 |
| 时间读数、召回片段、配角命中、本轮身份 | `<附注>` 尾注 | 每轮都变 |
| 会话档案卡 | 独立 user 消息 | 每 20 轮才重写一次，且排在固定窗口之后 |
| 摘要 | system（但**只在压缩那一刻**重写） | 若每轮重写摘要 = 每轮全量未命中 |

## 7 · 未来设想

> 4 个功能设想 + 1 个结构性重构。**除群组已有完整设计外，其余都还只是想法**。

### 7.1 群组（多角色同场）— 设计已定稿，未开工

目标：**角色按「剧情 / 意图 / 性格」自己决定要不要开口、该谁说、说什么；用户随时能打断。**

刻意排除两种做法：❌ 只有 @ 才答（那是命令行，不是交互）；❌ 点谁谁说（把编排权全交用户，群聊退化成一个人玩所有角色）。

拆成三个**有顺序**的判断：① 该不该有人开口（`silent` / `speak`）→ ② 该谁说 → ③ 他说什么（一句 brief 给下一跳）。顺序是有意的：先问①，才不会出现"只会选人"的判断器把群变成互相捧场。**沉默是合法输出，不是出错。**

已知硬约束：连续两条 assistant 消息的接口行为**未验证**，方案用"合并成一条 + `[名字]` 前缀"规避。

### 7.2 实时聊天背景 — 双模式

剧情场景切换时背景自动切换（到学校 / 到教室 / 到操场）。**成本由用户自己选**：

| 模式 | 准不准 | 延迟 | 成本 |
|---|---|---|---|
| **A. 内置图库** | 只认库里有的场景 | 0 | **0** |
| **B. 模型生图** | 任意场景都能出图 | 几秒～几十秒 | 每张计费 |

流程三步：① 场景判定（可复用前置钩子）→ ② 出图（查库 or 生图）→ ③ 换背景（挂点现成）。
未解决：生图用哪家、延迟怎么忍、同一场景怎么保持一致（场景 id → 图缓存？）、隐私（提示词会带剧情）。

### 7.3 自制音色 — 只有想法

让角色用自己的声音朗读。未定：音色从哪来（样本克隆 / 调参 / 组合现成音色）、谁来合成（现有 TTS 只有一家支持）、克隆他人声音的合规提示。

### 7.4 角色小手机 — 只有想法（有一个实机参考）

给每个角色一部"手机"，进 TA 的屏幕里聊天。参考某个市面产品（实机研究过）：它是**两层嵌套**——外层整屏模拟 iPhone（锁屏 / 主屏 / 小组件 / Dock），内层是个微信式四页应用。

我的想法比"皮肤"更进一步：**它要和 Gaia 联动**——

- Gaia 里建的角色会**自动建立一个「小手机」实例账户**；
- 角色在**聊天过程中能控制这台手机**（换壁纸、发动态、改签名、给你发消息）。

技术上真正难的是「**模型怎么控制**」，我看到三条路：

| 路径 | 做法 | 成本 |
|---|---|---|
| A. 隐藏块解析 | 模型回复里额外输出结构化块（如 `<phone>{...}</phone>`），前端截下执行、不显示给用户 | **0**（同一次请求） |
| B. 后置钩子再问一次 | 回复完单独请求一次"你这一轮做了什么" | 每轮多 1~3 分 |
| C. 真工具调用 | 给模型 tools / function calling | 取决于服务商是否支持 |

硬约束：状态**绝不能进 system**（否则每轮击穿缓存）、动作必须白名单、必须可审计可撤销、虚拟世界的消息不能混进真实会话表。

### 7.5 重构构想：多账户 + 角色级记忆（结构性前置）

这是所有设想的**前置工程**，也是 §4.6 那个缺陷的正解。

一句话：把「角色预设」从人格模板升级为**完整账户**，从**结构上**把两种机制分开：

```
机制 A → 内置账户（素材库）：只读、可检索、不进上下文、不整理
机制 B → 各角色账户：读写、压缩、整理、召回、档案卡
```

目标结构与分期（6 个阶段）：0 文档定稿 → **1 键注册表 + 账户作用域（地基）** → 2 内置账户=素材库 → 3 记忆系统重构 → 4 卡/包新格式（目录+zip）→ 5「取材做角色」应用内化 →（新增）6 角色小手机。

关键设计判断：

| 判断 | 理由 |
|---|---|
| 一个账户 = 一个角色的一整套系统 | 记忆不是"关联到角色"，是角色**内部的一层**，没有外键、没有跨角色共享 |
| 账户身份 `<角色名>-<短id8>`，id 不变名字可改 | 否则改名/换机记忆就断 |
| 设置三分：账户级 / 全局 / 灰区 | API Key、用户本人资料、界面语言必须全局；模型/上下文/皮肤可账户级 |
| 数据分界：可见可备份的放磁盘账户目录，运行时/派生放 IndexedDB（带 `accountId`） | 不建议 IndexedDB 按账户分库（迁移坑多） |
| 迁移必须可回滚 + 不删旧库 + 给自检输出 | 线上已有真实用户与真实记忆，这是最贵资产 |
| 文件系统：SAF 目录树为主 + 私有目录兜底 | 唯一同时满足"用户能看见/拷走/塞进来"且零敏感权限的方案 |

## 9 · 想请教的问题

> 这一章是本文的重点。分成五组，每组前两条是我最想听的。

### 9.1 记忆系统：结构应该怎么切

1. **多角色的记忆，你会按什么切？** 我打算按"账户/角色"物理隔离（每角色一套文件库），而不是加关联字段。这个方向对吗？有没有更轻量但同样干净的做法？
2. **记忆的"正确性"怎么评估？** 我现在只靠体感（会不会 OOC、会不会张冠李戴），没有任何定量指标。有没有可落地的"记住率/召回准确率"测法？
3. 关键词召回 vs 向量检索：在**中文角色扮演语料**（大量对话、专名多、语气词多）上，向量检索真的比"文档频率加权 + 稀有词锚点"更好吗？我的担心是向量召回在叙事文本上容易语义漂移。
4. 记忆文件该"持续蒸馏改写"还是"只追加不改"？我现在是前者（像做梦），但改写会丢细节。
5. 原文档案（`/archive/*`）只召回不注入，这个边界对不对？

### 9.2 成本与缓存

6. **动态内容还有没有比"尾注"更好的放法？** 我现在的做法是：静态进 system、动态全塞最后一条 user 消息的 `<附注>` 里。有没有既能保缓存、又能让模型"更重视"这些动态信息的办法（比如多个 system 段、或把动态内容作为额外的 assistant 消息）？
7. 长会话的窗口策略：现在是"固定 30 轮 + 整体丢弃 + 摘要兜底"。有没有更适合角色扮演的窗口/摘要组合？
8. 缓存命中率 73~85% 算正常吗？我怀疑还能更高——理论上除最后一条 user 消息外都该命中，但实测总差一截，可能是我哪里还在动 system。

### 9.3 角色卡与生态

9. **`chara_card_v2` 的兼容边界**：要不要也支持 lorebook / World Info 的格式？还是自建（配角库）更好？
10. 角色卡里塞记忆，你怎么看"卡 = 快照"这个定位？体积（含原文 1.5–2 MB）会不会太激进了？我的折中是默认不带原文。
11. 换机迁移：磁盘账户目录 vs 纯 IndexedDB，你倾向哪个？我担心 SAF 在各家 ROM 上的差异。

### 9.4 架构

12. **单 Activity + WebView 这条路，在"要做复杂交互（群聊、小手机）"时会不会撞墙？** 什么时候该考虑上原生或 RN？
13. 积木式三层 + 构建期强制边界，是不是过度设计？我的动机是防止功能互相长进对方身上，但代价是每加一个跨块交互都要先设计事件/插槽。
14. 零后端这个决定（隐私 + 无运营成本），在"要做跨设备同步"时是不是必然要推翻？

### 9.5 新功能

15. **角色"控制 UI 状态"**（§7.4）：隐藏块解析 / 后置钩子 / 真工具调用，你会选哪条？有没有我没考虑到的坑？
16. **群聊的终止条件**：我定了五种（沉默合法、附和禁止、默认 3 跳上限…），你见过更稳的编排方式吗？
17. 生图做背景：同一场景的一致性（第二次回到同一间教室画面不同）怎么破？
