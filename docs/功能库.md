### 2.4 记忆（三套独立机制，别搞混）

| 机制 | 是什么 | 存在哪 |
|---|---|---|
| 摘要压缩 | 滚动抽取式摘要（「问 → 答要点」），超预算丢最旧；压缩后 `dropTurns` 丢掉被覆盖的轮次 | IndexedDB `gaia.memory` |
| 长期记忆文件库 | 一个记忆 = 一个 Markdown 文件：`/profile.md`（用户是谁）、`/preferences.md`（怎么回答）、`/topics/*.md`、`/areas/*.md`、`/people/*.md`。空闲约 2 分钟后自动「做梦」整理，也可手动「立即整理」 | IndexedDB `gaia.memory.files` |
| 会话档案卡（防 OOC） | 长会话建一张卡：人物（姓名/年龄/身份/说话方式/称呼）、关系、世界要点、剧情进度、未完成线索 | IndexedDB `gaia.memory.card` |
| 关键词召回 | 命中旧轮次时把片段放进请求**末尾**（尾注），不进 system | 不落库，实时算 |
| 记忆文件召回（1.8.15 加权重） | 对 `/people` `/topics` `/areas` 正文做行级检索，命中才注入尾注。词权按「文档频率」算：df≤1 记 2 分、≤3 记 1.5、≤8 记 1、其余 0.5，4 字以上 ×1.5；「哥哥/姐姐/宝宝/亲爱/老公/老婆/主人/大人」与全虚词片段（「得了我」「了你」）权重直接归 0。标题/描述/别名命中 +2，单行 ≥1.5 才算命中 | 不落库，实时算 |
| 原文档案召回（1.8.15） | `/archive/*` 单独一条战线：命中那句前后各取 2 条成段注入（单段截 1200 字），预算 750 token、最多 1 段、总分门槛 3，且必须有一个「稀有词」锚点（权重 ≥1.5）才给——防止泛问句把整段原文拉进来。原文档案只读，整理器被明令禁止写入 | IndexedDB `gaia.memory.files`（`/archive/` 开头） |
| 记忆面板 | 设置 → 记忆：摘要（压缩轮数/时间/正文/清除）、会话档案（查看 / 用当前对话重建 / 删除）、长期记忆（逐文件编辑 / 删除 / 立即整理）、配角库入口 | — |

> 三个库分开存是有原因的：早先共用一个 `gaia.memory` 导致建表冲突（`NotFoundError … object stores was not found`）。

### 2.5 主题商城

| 组 | 可选 |
|---|---|
| 主题（配色） | 默认 · DeepSeek / QQ 蓝 / 微信绿 / 米纸 / 暗夜紫 |
| 气泡 | 默认 · DeepSeek / QQ 风 / 微信风 / 极简 / **透明**（1.8.13-beta.4 起） |
| 背景 | 默认 / 浅灰雾 / 蓝紫渐变 / 米纸纹 / 星夜 |
| 界面（骨架） | 经典 / **微信**（1.8.13-beta.3 起；换的是整套壳，见 §2.12） |

实现方式：前三组是纯 CSS 变量覆盖 + `html[data-gaia-skin|gaia-bubble|gaia-background]` 属性，**没有引入任何第三方 UI 库**；默认项不做覆盖，保持原观感。第四组「界面」不写 CSS，而是通过平台 `setLayout()` 切壳（`html[data-gaia-layout]` 只作标记）。点一下立刻生效，选择存 localStorage。

**透明气泡**：`data-gaia-bubble='glass'`，rgba 底色 + `backdrop-filter: blur()`，深色/星夜另有深色玻璃覆盖；旧 WebView 不支持 `backdrop-filter` 时退化成半透明纯色，仍可用。
**输入框透明**：只要背景不是「默认」，`[data-gaia-input]`（输入胶囊）与 `[data-gaia-input-dock]`（底部托底条）自动切成玻璃，白胶囊与白色渐变条会一起消失；背景=默认时完全不动。

### 2.13 会话配角库（1.8.15 起）

| 项 | 说明 |
|---|---|
| 入口 | 设置 → 记忆 →「打开配角库」（面板下半部分）；微信界面另有「我」页 →「配角库」一行 |
| 是什么 | 酒馆 lorebook 的最小等价物：**每个会话一套**配角档案。主角走角色提示词（system），配角只在本会话按触发词进尾注 |
| 字段 | 名字 / 触发词（别名、称呼，逗号分隔）/ 身份 / 说话方式 / 对「我」的称呼 / 与主角·我的关系 / 补充要点；两个开关：常驻（每轮都带）、启用 |
| 注入规则 | 命中范围 = 本轮提问 + 最近 6 条消息；大小写无关的子串命中；「常驻」无条件带。全部走 `tailNotes`（每轮变的段），**不进 system、不改历史**，所以不会击穿提示词缓存 |
| 预算 | 一次注入总字符 900（`CAST_BUDGET_CHARS`），单条正文截 260 字；按 `order` / 更新时间排序，超预算的后面的不进 |
| 导入导出 | 面板底部「导入 / 导出」，JSON（`schema: 'gaia.cast'`，v1）。导入一律落到**当前会话**、按名字去重（同名覆盖字段）；导出行走原生落盘（下载/Gaia） |
| 存储 | 独立库 `gaia.cast`（v1），按 `sessionId` 归属；别的会话的配角不会在本会话生效（面板底部会提示「别的会话里有 N 个配角」） |
| 代码 | `features/cast/`：`contract.ts`（字段 + 渲染 + 预算）、`middleware.ts`（命中与注入，order 10）、`store.ts`、`storage.ts`、`format.ts`、`ui/CastPanel.tsx`；`flags.cast`，order -50，返回键分级 56 |

## 3. 分域细节（改的时候看这里）

### 3.1 一次请求里到底装了什么（顺序即成本，别乱动）

```
system（字节稳定段，只有这里能命中缓存）
  ├─ 上游基础系统提示词
  ├─ 角色提示词 / 技能正文
  ├─ 早前对话摘要（压缩后才有；有会话档案时不再注入）
  └─ 长期记忆（画像 + 回答偏好全文；其它文件只给标题和描述）

messages
  ├─ 固定窗口内的历史（默认最近 30 轮，按滞回策略整体丢弃，不逐轮滑）
  ├─ [会话档案卡]（独立的一条 user 消息，动态内容，所以不进 system）
  ├─ [latest_reminder]（当前时间/时区，固定 5 字段格式）
  └─ 当前 user 消息（正文 + <附注> 尾注：时间读数、召回片段）
```

三条铁律（违反就变贵或报错）：

1. **每轮都会变的字节绝不能进 system**，否则提示词缓存从第一个字节就作废。
2. `latest_reminder` 只接受 `<date>,<weekday>,<location>,<platform>,<language>` 五个字段，且后面**必须紧跟**一条 `user` 消息；不能塞中文自由文本（会报 `unknown language`），也不能连着放两条。
3. 压缩会改写历史 → 必须同时 `prefixEnabled = false`，否则续写内容重复。

### 3.2 记忆的三个开关怎么配合

| 情况 | 行为 |
|---|---|
| 默认（会话档案关） | 摘要压缩按阈值工作；窗口 30 轮 |
| 会话档案开 + 该会话**已建卡** | 不注入抽取式摘要、不 `dropTurns`、不关续写前缀；长度交给固定窗口，人设交给档案卡；自动压缩也跳过（手动仍可压） |
| 会话档案开 + 还没建卡（< 40 轮） | 与默认一致；第 40 轮后的下一次发送前建卡 |

建卡成本：只取**开头 8k + 最近 16k token** 做样本，一次约 2~5 分钱；之后每 20 轮更新一次（约 2 分钱）。实测一张卡覆盖到第 6941 条消息，输入约 10751 token（≈1.1 分）。

角色卡预置卡（1.8.15 起）：卡里带 `extensions.gaia.sessionCard` 时，导入后按角色 id 存进 `gaia.memory.card` 的 `seeds` 表；该角色的**新会话首次发送前**自动落成正式档案卡（`seedInitialCard`），并顺手把「会话档案」开关打开。所以第一句就可能带旧剧情——是设计行为，不是串会话（诊断日志会写「会话档案卡就位（角色卡预置，覆盖到第 N 条）」）。

### 3.2b 配角库与记忆召回的成本边界（1.8.15）

| 东西 | 进哪 | 上限 | 代价 |
|---|---|---|---|
| 配角（命中/常驻） | 尾注 `tailNotes` | 900 字符/轮、单条 260 字 | 只有出场那几条花钱，且不动 system → 缓存照命中 |
| 长期记忆·相关条目 | 尾注 | 2 个文件 × 4 行，600 token | 同上 |
| 原文片段（`/archive/*`） | 尾注 | 1 段，命中行前后各 2 条、单段 ≤1200 字，750 token | 同上 |
| 会话档案卡 | 独立 user 消息（`cardNote`） | 一卡 | 每 20 轮改写一次，但它在固定窗口之后，不影响前缀缓存 |

三条召回的战线上限都**不在 system**；谁要把它们挪进 system，长会话每句话都会按未命中计费（§5）。

### 3.3 主题商城怎么加一套新的

1. `features/theme/catalog.ts` 里往 `SKINS` / `BUBBLES` / `BACKGROUNDS` 加一项（`id` 即 CSS 选择器里的值）。
2. `features/theme/theme.module.css` 里加对应的 `:global(html[data-gaia-skin='xxx'])` 变量覆盖块；气泡用 `[data-bubble='me']` / `[data-bubble='ai']` 挂点，背景用 `[data-chat-surface]`。
3. 深色背景必须**同时**覆盖 `--dsw-alias-label-*`、`--dsw-alias-bg-layer-2/3`、`--dsw-specific-bubble`，否则出现"黑底黑字、啥也看不见"（星夜就是这么修的）。

### 3.4 已知的界面挂点（写 CSS 时要用的）

| 选择器 | 挂在哪 |
|---|---|
| `[data-chat-surface]` | 会话视图根节点（背景画在这） |
| `[data-bubble='me']` | 我方消息气泡 |
| `[data-bubble='ai']` | 助手回复容器（`.bubbleArea`，默认 `display: contents`） |

## 5. 钱与缓存（为什么这么排）

DeepSeek 的缓存是**前缀逐字节匹配**：只要前缀里有一个字节变了，从那一段往后全部按未命中计费。

| 观察值 | 说明 |
|---|---|
| 缓存命中 0% | 新会话 / system 变了 |
| 缓存命中 ~20% | 有东西改写了 system（历史上是压缩改写摘要造成的） |
| 缓存命中 73~85% | 正常。只有最后一轮的用户消息不同（尾注不落库，所以永远差这一条） |

**实测费用**（flash、闲置时段、开思考+搜索）：

| 场景 | 输入/命中/输出 | 约 |
|---|---|---|
| 最高执政官 第 1 轮 | in 8248 · 命中 0 · out 222 | 0.91 分 |
| 同一会话 第 2 轮 | in 1246 · 命中 7168(85%) · out 233 | 0.23 分 |
| 心理老师 第 1 轮 | in 6375 · out 574 | 0.70 分 |
| 同一会话 第 2 轮 | in 1316 · 命中 5120(80%) · out 574 | 0.37 分 |

所以长会话"两句话八毛"的根因通常是：**每轮都在改 system**（摘要重写、时间/记忆塞进 system），而不是窗口太长。

## 7. 已知问题与坑

### 7.1 附件发送报「对话或附件尚未保存到本机，关闭页面可能丢失，请重试」

- 现象：选图发送时弹这句，之后「重试」卡住；消息里的图片显示成文件卡片而不是缩略图。
- **已定位（11-20，用户诊断日志 + 截图）**：1.8.13 把 `File → Blob` 的转换写在了已经打开的 readwrite 事务里。`await blob.arrayBuffer()` 读磁盘、让出事件循环，事务就被浏览器自动提交（日志：`TransactionInactiveError … The transaction has finished`，紧接着 `InvalidStateError … objectStore`）。后果是**会话正文也没写进去**，`pendingFiles` 永远清不掉，之后每发一条消息都把同一批附件再试一遍、再失败一遍——「重试」无效就是这么来的。与配额无关（用户 91.9 MB / 64596 MB）。
- **1.8.13-beta.1 已修**：先转换再开事务；每个原件各写各的事务（真写坏只丢那一张）；会话 + 摘要独立事务。真机（Android 16 真机）实测：带图发送无报错，杀进程重开消息、缩略图、助手回复都在。
- 残留（未改）：附件刚发出去那一瞬间仍显示文件卡片，切走再回来（或重开）才变缩略图 —— 见 §7.2。

### 7.3 新页盖在设置页下面（1.8.13-beta.2 踩到）

- 现象：从设置页点进自己写的整屏页（`app.overlay` 槽位），点完「没反应」，其实页面已经渲染，只是被设置页盖住了。
- 原因：`settings.module.css .overlay` 是 `position: fixed; z-index: 60`；新页若写 `position: absolute; z-index: 40`，同层比 z-index 必输。
- 规矩：**挂在 `app.overlay` 上的整屏页一律 `position: fixed` 且 `z-index ≥ 61`**（服务商页用 70）。`order` 只管 DOM 顺序，不管层叠。

### 7.4 列表行契约与 CSS 优先级（1.8.13-beta.3 踩到）

- 现象：微信壳「通讯录」的行挤成两行（头像一行、名字一行，行高变成 150），因为 `display: flex` 没生效。
- 原因：壳里给行定的基样式是 `.root :global([data-shell-row])`（类 + 属性，特指度 0,2,0），把 `display: block` 写进去了；角色积木自己的 `.contactRow { display: flex }`（0,1,0）压不过它。
- 规矩：**`[data-shell-row]` 基样式只管底色/分线/字体/字号**，`display` 与内边距留给使用方（我页的 `.rows` 再补 `display: block`）。跨块的列表行统一带 `data-shell-row` 属性，壳按属性给皮，积木只管内容。
- 另外：`[data-shell-row]` 的规则写在 shell 的 module.css 里，深色模式要同时用 `:global(body.dark)` 覆盖一遍，否则深色下是白底黑字。

### 7.5 切壳时看不到变化（是正常的）

- 现象：在「主题商城」里点「微信」，界面没动。
- 原因：商城自己是 `app.overlay` 上的整屏页，盖在壳上面；壳已经在下面换好了。
- 验收时记得先关掉商城（返回两级）再看。另：切壳期间不要连按返回——最后一记返回会交给原生，直接退到上一个应用（可能是微信本体，别在人家聊天列表里乱点）。

### 7.6 玻璃效果的两个前提（1.8.13-beta.4 起）

- `backdrop-filter` 需要 WebView 支持（Android 16 真机正常）。旧机不支持时会退化成"半透明纯色"，气泡/输入框仍能看清文字，只是没有毛玻璃。
- 玻璃只在**有东西可透**时才好看：背景=默认（纯底色）时「透明」气泡几乎和页面同色，卡片说明里已经写明"配渐变/图片背景最好看"。
- 输入框玻璃挂在 `[data-gaia-input]`（ChatInput 胶囊根）和 `[data-gaia-input-dock]`（SessionView 底部托底条）上；改这两个组件时别把属性删了，否则背景非默认时又会出现白胶囊 + 白渐变条。

### 8.2 出包与装包

```powershell
# 出包（注意：.ps1 必须存成 UTF-8 with BOM）
powershell -NoProfile -ExecutionPolicy Bypass -File <repo>\scripts\build-all.ps1 `
  -VersionName 1.8.15 -VersionCode 1208

# 装包（先 force-stop，否则可能出现"安装成功但没换版本"）
adb shell am force-stop com.dialogshell.app
adb install --no-incremental -r <repo>\android\out\gaia-1.8.15.apk
```

版本码规则：`1000 + 主次补三位` → `1.8.13 = 1193`。只能增不能减，否则 `INSTALL_FAILED_VERSION_DOWNGRADE`。

> 公式只管到 1.8.13；1.8.14 起在公式值之上顺着 beta 递增（1193 → 1194…1200 → 1.8.14 = 1201 → 1207 → **1.8.15 = 1208**）。新版本号算出来的公式值若低于当前最高码，以"当前最高 +1"为准。

> 装包务必加 `--no-incremental`：vivo/Android 16 上走 Incremental Install 会弹权限确认，无人值守时返回 `INSTALL_FAILED_ABORTED: User rejected permissions`（包本身没问题，改用 Streamed Install 即 Success）。

## 10. 群组（多角色同场）：已定设计，未开工

> 这一节是**设计定稿**，不是已发布功能。开工时按 §10.9 分期，P1 第一刀在 §10.8。

### 10.1 目标（一句话）

**角色按「剧情 / 意图 / 性格」自己决定要不要开口、该谁说、说什么；用户随时能打断。**

明确排除两种做法：

| 不做 | 为什么 |
|---|---|
| ❌ @ 才答 | 要用户点名才动，那是命令行，不是交互 |
| ❌ 点谁谁说（星野的做法） | 把编排权全交给用户，群聊退化成"一个人玩所有角色" |

### 10.2 三重判断：拆成三个**有顺序**的问题

| 顺序 | 问题 | 依据 | 输出 |
|---|---|---|---|
| ① | 该不该有人开口？还是此刻就该沉默？ | 剧情轴 + 意图强度 | `silent` / `speak` |
| ② | 该谁说？ | 意图指向 + 性格轴 | 成员 id / `null` |
| ③ | 他说什么？ | 剧情轴 + 性格 | 一句 brief（给下一跳的指令） |

顺序是有意的：先问①，才不会出现"只会选人"的判断器把群变成互相捧场。**沉默是合法输出，不是出错。**

三轴的数据来源：

| 轴 | 数据 | 存在哪 |
|---|---|---|
| 剧情 | 群设定（≤200 字）+ 关系表 + 剧情进度（复用会话档案卡的「剧情进度 / 未完成线索」）+ 最近 6 条 | 群设置 / `gaia.group` / `gaia.memory.card` |
| 意图 | 硬信号：点名、@、"记一下…"这类系统陈述 → 零成本直接定；软信号：「你」在群里有歧义、提问、指控、玩笑、留白 → 交判断器 | 当轮消息 |
| 性格 | `traits`（一行性格，如"寡言，只在被问到专业问题时开口"）+ `initiative`（0~1 发言意愿，默认 0.5） | 角色新增两个**可选**字段 |

老角色不要求手填：**进群时自动派生一次**（小模型把 `systemPrompt` 压成一行 traits + 估一个 initiative），存进角色，之后可在角色编辑页改。

判断器输出（可解释，界面能点开看"为什么是他"）：

```json
{"mode":"speak","speaker":"lin",
 "brief":"王五刚把话头递给你，一句话接住，别抢话",
 "why":{"plot":"冲突刚起，需要有人退一步",
        "intent":"他问的是「你」，但上下文里只有你知道这件事",
        "personality":"寡言，但被点名就会答"},
 "confidence":0.7}
```

- `mode:"silent"` → 这一轮停（界面显示"没有人接话"）
- `mode:"end"` → 整条链结束
- 判断器失败 / 超时 → **默认 end**（宁可安静，不可乱说）

### 10.3 链式轮次与终止条件

```
用户发一句
  → [1] 说话人 A（system 含群规+全体人格，尾部指定身份）
  → [2] 判断器：谁还要接？接什么？还是结束？
  → [3] 说话人 B（A 的话在它输入里，它会真的回应 A）
  → [2] 判断器 …
  → 停
```

补充规则：**A 的文字里 @ 了 B → 跳过判断器直接唤醒 B**（省一次调用，也让互相点名很自然）。

必须同时成立的 5 个终止条件：

1. 判断器输出 `next: null`
2. 跳数用完（默认 **3**）
3. 本轮累计输出超过预算（默认 **8000 token**）
4. 用户插话
5. 用户按停止

### 10.4 打断协议（核心难点）

**现状是个硬坎**：`services/chat/store.ts` 的 `sendMessage` 里有

```ts
if (sessionId !== null && (… || getStreamController(sessionId) || …)) return false
```

也就是**机器人正在说话时，用户发出去的话会被静默丢掉**。要让"随时打断"成立，必须：

1. 新增平台钩子 `registerSendInterceptor`（由 `group` 积木注册）：发送前先 `interruptChain(sessionId)` —— 中止当前流、清空队列、丢弃判断器结果，然后再正常发送。
2. **generation 计数**：每跳结束后先核对 generation；不一致就再也不排下一跳，防止"用户已插话，上一跳的 await 结束又把 B 叫起来"。
3. **停止按钮不用新接口**：`stopReply` 只 abort 当前流；链在每跳结束后看这条回复的 `status === 'stopped'` → 整条链终止。
4. **半截消息**保留为 `stopped`（上游已有该状态）；可做成群设置「打断即删」，默认保留。

### 10.5 装配：不破坏缓存，也不赌未验证的接口行为

| 位置 | 放什么 | 为什么 |
|---|---|---|
| system 最前 | 群规（短）+ **全体成员人格块（固定顺序）** + 关系表 | 发言人切换时 system 不变 → 缓存能**跨发言人命中** |
| 尾部（附注） | 「本轮由 X 作答；刚才是 Y 说的」 | 动态内容，符合"静态进提示词、动态进尾部" |
| 请求历史 | 上一跳的合成指令（**不落库**） | 保证 user/assistant 交替，界面不多出气泡 |
| 连续 assistant | 合并成一条，各自加 `[名字]` 前缀 | 规避"连续两条 assistant"的未验证行为，也让模型分清谁说的 |

合成指令走 `streamReply(sessionId, reply, { history, question })` 的 `question` 参数——**只进请求、不进会话**。

代价：system 变大（每人 500~2000 token），但那是命中价；4 人 × 1500 token ≈ 每轮 0.012 分钱，可忽略。若按直觉写成"谁的 prompt 当 system"，每换一个发言人整轮缓存全废，4 人群每句话都按未命中计费——这正是"两句话八毛"的翻版。

### 10.6 成本闸门与默认值

| 闸门 | 默认 | 理由 |
|---|---|---|
| 跳数上限 | 3 | 剧情可以很长，钱包不行 |
| 同一人连续发言 | 禁止（被直接点名除外） | 防一个话痨占满全场 |
| 最近 3 跳说过话的人 | 降权 | 防两人对答把第三人晾着 |
| 附和 | 判断器提示词里明确禁止"只是附和/重复上一句" | 防"是啊""确实"刷屏 |
| 本轮输出预算 | 8000 token | 说不完就停 |
| 判断器失败 | 默认 end | 出错宁安静 |
| 判断器模型 | flash | 每跳约 0.2 分 |

量级：3 跳的一轮 ≈ **3 倍单聊 + 0.6 分**；判为 `silent` 只花那 0.2 分。UI 要实时显示"这一轮还能接 N 句"。

### 10.7 参考案例

**Grok Bot**（[行为对照](https://github.com/milind-soni/openmausbot/blob/main/docs/plans/2026-09-02-bot-concurrency.md)、[团队 Bot 通报](https://zapier.com/blog/grok-bot/)）

| 借 | 不借 |
|---|---|
| bot 是**人格**不是副本，一个 bot 进多个群 | 常驻 24h agent、每人一台电脑 |
| **一个 bot 同时只有一个 turn**；群里 host 逐个唤醒成员 | webhook / 跨房间共享上下文 |
| bot 之间是**异步唤醒**（@ 才理） | 审批队列那套运营机制 |

**星野**（[实测长文](https://m.163.com/dy/article/J1VTDICM0511N33R.html)、[建群教程](https://www.xiaohongshu.com/discovery/item/678a2be20000000019033ba7)、[测试版实测](https://www.xiaohongshu.com/discovery/item/65c9ffc5000000002c036b68)）

它的群聊是**导演制**：最多 5 人、建好不能增删；群描述（剧情/目的/关系）显著影响对话；每人可设开场白；发言顺序可调；**不自动说话，点谁的头像谁才回一句**；另有回复提示、回溯、重启。

| 它的实测问题 | 根因 |
|---|---|
| 群聊里角色**忘记人设** | 所有人格塞同一上下文互相污染，缺"我是谁"的每轮锚点与档案回注 |
| **随机性过高**，要用户自己控场推进剧情 | 没有剧情状态机：谁该说、戏走到哪全靠即兴 |
| 群描述写多了**一直重复同一句话** | 提示词过载（设定+规则+人设挤在一个 system，模型退化成复读） |

| 抄 | 不抄 |
|---|---|
| 群描述 = 剧情种子，**且必须短**（限 200 字） | 必须点头像才说话（那等于没有交互） |
| 人物关系单独一层 | 建群后不能增删角色 |
| 每人一句开场白（也是判断器的风格锚点） | 把设定与规则全塞进一个群描述 |
| 发言顺序作兜底 / 平票 | |
| 点头像 → **定向补一句**（不打断整条链） | |
| 回复提示（你不知道说什么时给 2~3 个选项） | |
| 重启这一场（清上下文 + 重放开场白） | |

### 10.10 待定与风险

**要你拍板的两件事**：

1. 性格数据用"进群时自动派生 traits + initiative，之后可改"——接受吗？
2. "没有人接话"要不要显性显示（一条灰字），还是宁可让判断器硬选一个人？

**风险清单**：

| 风险 | 处理 |
|---|---|
| 连续两条 assistant 的接口行为**未验证** | 用"合并成一条 + `[名字]` 前缀"规避 |

### 11.2 逐条记录（想法原文 + 待澄清）

**① 群组（多角色同场）**

- 完整设计已定稿：目标、三重判断、链式轮次、打断协议、装配、成本闸门、数据模型、P1 分期都在 §10，可直接开工。
- 唯一硬约束：连续两条 assistant 的接口行为**未验证**，方案用「合并成一条 + `[名字]` 前缀」绕开。
- 与配角库（§2.13）的关系要先定：群成员算不算"配角"的一种。

**② 实时聊天背景**

想法（操作者 2026-11-22 原话）：**剧情场景切换的时候背景也实时切换**——说到学校了、到教室了、到操场了，都是不同的场景，剧情进行到这里可以实时切换。
实现路径：**后端要有一个生图模型**才能解决——AI 和用户去聊，到场景了就给生图模型指令，生图模型去生图然后自动切换。

**成本由用户自己选**（操作者 2026-11-22 补充原话）：成本问题确实有考虑，所以可以让选择——选**系统自带的背景图库**还是**模型生图**。模型更好是实时、更准确，但坏处就是成本高、有延迟。

也就是说这功能**从一开始就设计成两条可切换的路**，不是"先做一条以后再说"：

| 模式 | 准不准 | 延迟 | 成本 | 覆盖不到的场景 | 建议默认 |
|---|---|---|---|---|---|
| **A. 内置图库** | 靠人工预置，只认库里有的场景 | 0（本地切换） | **0** | 退回默认背景，不换 | **✅ 默认** |
| **B. 模型生图** | 任意场景都能出图，最贴剧情 | 几秒～几十秒 | **每张计费** | 基本都能覆盖 | 关（用户主动开） |

> 默认值按"成本优先"取 A。**这条待你最终确认**：也可以默认 B（体验优先但自动花钱），或首次开启时弹一次说明再让用户选并记住。

拆成三步看（两条路共用 ①③，只有 ② 不同）：

| 步 | 做什么 | 落点 |
|---|---|---|
| ① 场景判定 | 每轮（或每 N 轮）让模型判断「现在在哪个场景」，输出场景 id + 场景描述 | 可复用 `beforeReply` 前置钩子（§1 平台层） |
| ② 出图 | **A 图库**：场景 id 查本地/预置图库；**B 生图**：把场景描述交生图模型 | A 是查表；B 是**全新一类外部调用**，现在完全没有（§2.11 只接聊天） |
| ③ 切换 | 拿到图 → 换 `[data-chat-surface]` 背景 | 挂点现成（§3.4），主题商城已有 5 套静态背景可作兜底 |

**还有一个可选变体（要不要做请你定）**：**A→B 混合**——先查图库，命中就用（0 成本、0 延迟），**没命中才生图**。这样大部分常见场景免费，只有新场景花钱，成本与体验最平衡，但实现要管两套来源与回退。

**开工前必须问清的**：

| 问题 | 为什么要先问 | 是否已被"双模式"解决 |
|---|---|---|
| 生图模型用哪家？ | 服务商体系（§2.11）只覆盖聊天协议，生图是另一套 API、另一套 Key、另一套计费 | 未解决（选 B 模式才需要） |
| 延迟怎么忍？ | 生一张图几秒到几十秒，剧情是连续的 | **部分解决**：A 模式无延迟；B 模式仍要给「先切模糊占位、出图再淡入」或「场景稳定再生」 |
| 一致性怎么办？ | 第二次回到同一间教室，生成的画面会和第一次不一样 | **部分解决**：A 模式天然一致；B 模式仍要「场景 id → 图」缓存、固定 seed 或只生成一次 |
| 频率闸门？ | 不设闸就是每句都生图 | **部分解决**：B 模式要给「同一场景不重生」「每 N 轮最多一次」「预算上限」 |
| 隐私边界？ | 发给生图模型的提示词会带剧情内容（可能很私密） | 未解决：要不要只发场景描述、不发对话原文 |
| 失败怎么降级？ | 生不出来 / 超时 / 超预算 | **已明确**：B 失败就退回 A 的图库图，再退默认背景 |
| 钱怎么算？ | 生图单独计费，和聊天 token 两笔账 | **已明确**：A 免费；B 必须单列成本 + 预算闸 + 默认关 |

**A 模式（图库）自己要定的**：

- 图库从哪来？① 随包内置（打包进 assets，体积涨）；② 用户自建（导入图片，自己贴场景标签）；③ 两者都支持。
- 场景表怎么定？是固定枚举（教室/操场/卧室/街道…）还是模型自由输出后模糊匹配到最近的库内场景？
- 内置多少张、多大体积？要算进 APK 体积（现约 2.08 MB，塞几十张背景会明显变大，可考虑放服务端按需下载）。

- 现状可复用：背景挂点 `[data-chat-surface]`（§3.4）；主题商城已有 5 套静态背景（§2.5）就是 A 模式的雏形。
- **建议的第一刀**：只做 A 模式（场景判定 + 图库切换），把链路走通；B 模式与混合模式留作二期。这样不依赖任何外部服务，也没有成本争议。

**③ 自制音色**

- 想法：用户自己做音色，让角色用自己的声音朗读。
- 待澄清：
  - 音色从哪来？① 上传音频样本克隆；② 自己调参合成；③ 只用服务商现成音色但允许自选组合。
  - 谁来合成？现在朗读音色是单一默认（海星），接 TTS 要选定服务商——而 §2.11 已经记录「语音只有 DeepSeek 官方支持，别家会直接告诉你」。
  - 克隆涉及第三方声音，是否要加"仅限本人声音"的提示。
- 成本影响：语音不走聊天 token，但走 TTS 计费，要在方案里单列。

**④ 角色小手机**

- 想法：给每个角色一部「手机」，进 TA 的屏幕里聊天（类似"角色手机"类玩法的界面外壳）。

**参考实现：only max**（操作者 2026-11-22 指定：「我手机里面的 onlymax 这个 app，它就是一个小手机 app」）

实机查看记录（包名 `top.onlymax.com`，versionName 1.0，Android 16 真机）：它**不是一层皮肤，是两层嵌套**。

| 层 | 内容 |
|---|---|
| **外层：假手机** | 整屏模拟一台 iPhone——金属边框、灵动岛、假状态栏（时间/信号/WiFi/电量）、**锁屏**（大时钟 + 日期）、**主屏**（小组件网格 + 图标 + 页点 + Dock），右上角 `×` 退出 |
| **内层：微信式应用** | 点 Dock 的「Only max」进去，是一个四页应用：**会话 / 通讯录 / 发现 / 我**，与 Gaia 的微信壳（§2.12）几乎同构 |

外层主屏的**小组件**（信息密度主要靠它们，不是靠图标）：

| 小组件 | 显示什么 |
|---|---|
| 和 TA 的 N 天 | 在一起第几天，「自 2026-11-17 起」 |

内层四个页的结构（照抄它的做法）：

- **会话**：搜索 + 会话列表；空态「还没有会话，去『通讯录』添加 AI 好友，或发起群聊」
- **通讯录**：`添加 AI 好友` / `发起群聊` + 好友列表
- **发现**：动态圈 / 视频号 / 直播 / 扫一扫 / 吃顿饭 / 看一看 / 搜一搜 / 购物 / 小程序（完整照微信的目录）
- **我**：头像 + `Only ID` / 支付 / 收藏 / 动态圈 / 相册 / 表情 / AI 设置 / 赞赏作者

**创建 AI 好友的表单**（这个设计很值得借）：

- **人设模板**（点一下填入）：温柔闺蜜 / 毒舌损友 / 冷静学长 / 小猫娘 / 沉默守护者
- **基本信息**：头像（上传本地图片）/ 名字 / 人设（性格、说话方式、背景故事…）/ `TA 叫我` / `TA 在城市`
- **城市那一行的说明**：「填了城市，一起听歌会按真实球面距离算你俩隔多远，天气里也能直接切到 TA 那座城。城市名要能被地图认出来，保存时会自动核对。」

**图标的两类行为**（实测）：点信封图标直接跳去了**真实抖音**；从网页版进来后它显示「真站拒绝被内嵌窗口加载，已用软件内独立页面打开」，并给 `再打开 / 看内置抖音 / 浏览器` 三个兜底按钮。也就是说——一部分图标是**真 App/真站外链**，一部分是**应用内页面**，两者混在同一个桌面里。

**对 Gaia 的启示（候选做法，未定）**：

| 档位 | 做多少 | 成本 |
|---|---|---|
| 最小 | 只做外层：现有聊天页套一个手机框 + 假状态栏，Dock 只有「会话」 | 低，纯 CSS/布局 |
| 中等 | 加主屏小组件，每个都是**现有数据的另一种呈现**：恋爱天数（会话创建日）、亲密度（消息数/天数）、待办（复用记忆文件）、时钟（现成时间读数） | 中，要新页面与派生数据 |
| 较重 | 天气 / 距离 / 一起听歌这类要**真接外部数据**（天气 API、地图城市校验、音乐源） | 高，新外部依赖 |
| 完整 | 相册 / 动态圈 / 收藏 / 表情各自成独立页，要新数据模型与新库 | 高 |

- 与 Gaia 现状的关系：Gaia 已有微信壳（§2.12）四页底栏，小手机是「**再往外套一层**」，两者不冲突、可叠加。
- 落地建议（未定）：做成第三套 `AppLayout` 值 `phone`（`platform/layout.ts` 机制现成），**不要**在微信壳里加子页；仍守 §1 的**单 Activity**。

  - 假状态栏的时间/信号/电量是**装饰**还是**读真机**？（only max 的锁屏时间与主屏时间是同一套假数据）

### 11.3 排序建议（未定，等你确认）

1. **群组**——设计已定稿，且配角库已铺好路，直接可开 P1。
2. **角色小手机（只做皮肤层）**——纯界面，不碰数据、不依赖外部服务，风险最低。
3. **实时聊天背景·A 模式（内置图库）**——零成本零延迟，只做「场景判定 → 查图库 → 切换」链路；主题商城的 5 套背景就是雏形。
4. **实时聊天背景·B 模式（模型生图）**——要先定服务商、延迟方案、一致性缓存、预算闸；A 模式跑通后再接，失败直接回退 A。
5. **自制音色**——依赖外部 TTS 选型与计费。

> 生图与 TTS 都是「新的外部计费通道」，两条都需要先在 §2.11 服务商体系里加一类通道，可以在同一轮里一起铺路。

> **待确认的默认值**：实时背景 A/B 模式的默认值，我暂按「A 内置图库」记录（成本优先）。若你更想默认 B（体验优先但会自动花钱），或首次开启时弹说明让用户选，说一声改。开工时这两项（开关 + 默认值）要正式写进 §4 默认值表。
